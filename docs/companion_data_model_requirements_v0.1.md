# Companion Data Model：宠物需要收集哪些信息
## ——面向共生型 AI 成长伙伴的数据需求、边界与原则总结

> 项目：Co-evolving AI Companion / 共生型 AI 成长伙伴  
> 文档主题：Companion Data Model / 宠物需要收集哪些信息  
> 版本：v0.1  
> 日期：2026-10-15  
> 状态：需求与概念设计阶段  
> 说明：本文只讨论“需要什么信息、为什么需要、哪些信息不该收集、哪些信息能用于何种判断”。不讨论数据库设计、字段定义、具体算法、技术栈和工程实现。具体方案待后续完成相关项目调研后再确定。

---

# 1. 本阶段讨论的目标

当前要解决的问题不是：

> “宠物技术上能收集哪些数据？”

而是：

> **为了长期陪伴、理解用户的人格发展 / 心智发展，并在合适的时候进行介入，宠物真正有必要知道哪些信息？**

整个项目应坚持：

> **不是能收集什么就收集什么，而是只收集真正有助于陪伴、理解和成长的信息。**

因此这一阶段更关注：

- 信息的必要性；
- 信息在系统中的意义；
- 信息能支持什么判断；
- 哪些信息不能被过度解释；
- 哪些信息不应该默认收集；
- 哪些信息适合长期保留，哪些只适合短期使用；
- 如何避免系统变成监控工具或 life-logging 系统。

---

# 2. 核心原则：最小采集，而不是最大采集

对于一个长期陪伴用户数月、数年甚至更久的系统，最大的风险之一是：

> 为了“更懂用户”，不断扩大数据收集范围。

这会带来几个问题：

- 噪声越来越多；
- 用户模型越来越难解释；
- 隐私风险不断增加；
- 系统容易错误地把偶然行为解释成人格特征；
- 用户会产生被监控感；
- 最终偏离“宠物 / Companion”，变成行为监控工具。

因此建议确立一个长期原则：

# Collect minimally.

中文：

> **只收集完成陪伴与成长理解所需的最少信息。**

更进一步：

> **如果某类信息不能明显提升陪伴质量、状态判断或长期成长理解，就没有必要默认收集。**

---

# 3. 宠物需要理解两种完全不同的东西

前面的讨论已经明确：

Companion 同时关注：

## 3.1 用户此刻怎样生活

例如：

- 是否已经持续工作很久；
- 是否已经很晚；
- 是否长时间没有停下来；
- 是否反复回到同一个问题；
- 是否正在经历高强度投入。

这一部分主要服务于：

> **State Intervention / 当下状态介入**

例如：

> “已经很晚了，这个问题今晚一定要解决吗？”

---

## 3.2 用户长期怎样与世界相处

例如：

- 是否总在未完成状态下难以停止；
- 是否习惯不断把现在让位给未来；
- 是否总通过增加信息来降低不确定性；
- 是否长期处在“先完成，再生活”的模式里；
- 是否逐渐学会允许一些事情暂时没有答案。

这一部分主要服务于：

> **Development Intervention / 人格与心智发展介入**

例如：

> “我发现只要重要事情还悬着，你通常都会把休息往后推。”

这两类理解需要不同的信息基础，不能混为一谈。

---

# 4. 建议信息分为八大类

当前可以将 Companion 所需信息分为八类：

1. State Data  
2. User Action Data  
3. Interaction Data  
4. Context Data  
5. Semantic Data  
6. Self-report Data  
7. Longitudinal Pattern Data  
8. Relationship Data

这八类的意义不同，不能统一视为“用户画像数据”。

---

# 5. State Data：当前状态信息

State Data 回答的是：

> **用户现在处于什么状态？**

例如：

- 当前时间；
- 当前是否处于深夜；
- 当前连续活跃时间是否很长；
- 是否长时间没有明显停顿；
- 是否持续围绕同一任务；
- 是否频繁重新回到同一问题；
- 是否处于明显持续高强度交互状态。

这类信息的主要价值在于：

> 支持轻量、即时的状态介入。

例如：

> “我们已经在这里待了很久了。”

或者：

> “已经很晚了，这件事今晚必须解决吗？”

---

# 6. State Data 不能直接用于人格判断

这是非常重要的边界。

例如：

> 用户连续工作 4 小时。

可以说明：

> 用户现在持续工作时间较长。

但不能直接说明：

- 用户焦虑；
- 用户控制欲强；
- 用户逃避情绪；
- 用户无法接受不确定性；
- 用户有某种人格类型。

同样：

> 用户凌晨仍在工作。

可以触发一次轻量状态提醒。

但不能直接形成：

> “用户习惯牺牲生活给未来目标。”

后者必须依赖长期、跨情境证据。

因此：

> **State Data 主要描述“现在”，不能直接定义“这个人”。**

---

# 7. User Action Data：用户明确做出的选择

User Action Data 是比一般活动数据更重要的一类。

它回答：

> **用户自己明确做了什么？**

例如：

- 主动继续；
- 主动停止；
- 暂停；
- 重新打开某个问题；
- 改变目标；
- 缩小范围；
- 扩大范围；
- 接受当前答案；
- 要求更多证据；
- 决定今天先不解决；
- 主动放弃一个方向；
- 主动开始一个新方向。

这类信息与 Hermes 自动重试、自动搜索完全不同。

因为：

> **这是用户自己的选择。**

所以 User Action Data 可以成为长期行为分析的重要证据。

---

# 8. Interaction Data：用户如何回应一个具体情境

这一类可能是整个系统最有价值的信息之一。

它不只记录：

> 用户做了什么。

而是记录：

> **用户在什么情况下做出了什么选择。**

例如：

```text
Agent 已经给出一个可行答案
↓
Agent 建议停止继续搜索
↓
用户选择继续寻找更多证据
```

这个信息比单纯记录：

> “用户说了继续。”

更有意义。

因为它描述了：

> 情境 → 用户回应

这有助于观察用户如何面对：

- 不确定性；
- 失败；
- “够用但不完美”的答案；
- 多个选择；
- 暂时无法解决的问题；
- 停止点；
- 改变方向；
- 坚持与放下。

---

# 9. Hermes 数据的正确角色

前面的讨论已经明确：

> **Hermes 的自主行为不能直接代表用户。**

Hermes 自己：

- 搜索很多次；
- 自动 retry；
- 自动切换方案；
- 自动调用很多工具；
- 自己进行长时间 reasoning；

首先反映的是：

- Agent 行为；
- 任务复杂度；
- 系统策略；
- 工具和模型状态。

不能直接推出：

> 用户本人就是怎样的人。

因此 Hermes 对 Companion 的真正价值是：

> **提供任务背景、Agent 状态和用户选择节点。**

真正值得用于用户发展模型的是：

> 用户如何回应 Hermes 给出的结果、失败、不确定性、建议和停止点。

核心原则：

# Observe the choice, not the agent loop.

---

# 10. Context Data：用于防止误判的信息

Context Data 并不是为了“分析人格”。

它最重要的作用是：

> **让系统知道某个行为是否有合理的特殊原因。**

例如：

用户凌晨两点还在工作。

如果没有上下文，宠物可能误认为：

> 用户又进入长期过度工作模式。

但实际可能是：

- 明早有 deadline；
- 出现线上故障；
- 临时必须完成；
- 用户当天作息特殊；
- 用户明确表示今晚就是特殊工作安排。

所以：

> **行为必须放在情境里理解。**

Context Data 是一个重要的“防误判层”。

---

# 11. Context Data 不应该被滥用

Context Data 的作用是：

> 解释行为。

而不是：

> 无限扩张数据采集。

例如，为了知道某次深夜工作是否特殊，不代表系统就应该默认读取：

- 全部日历；
- 全部邮件；
- 全部项目文件；
- 全部浏览历史。

设计原则仍然应该是：

> **只获取足以解释当前行为的必要上下文。**

---

# 12. Semantic Data：对话里的语义信息

Semantic Data 指用户在 Hermes、ChatGPT 等对话中表达的内容。

其中可能包含：

- 当前关注的问题；
- 决策理由；
- 价值判断；
- 对自己的评价；
- 对生活状态的描述；
- 对成长变化的反思；
- 对某件事情为什么难以放下的解释；
- 对未来和当下的理解。

这些信息对于人格发展 / 心智发展非常有价值。

例如用户明确表达：

> “事情悬在那里我会一直想着。”

或者：

> “我以前总觉得等这一阶段结束以后再生活。”

这类内容很可能比单纯行为统计更接近真正的发展主题。

---

# 13. Semantic Data 的问题：信息量大、噪声高、隐私敏感

原始会话里会混合大量：

- Agent 自主生成内容；
- 临时任务信息；
- 代码；
- 搜索结果；
- 无关细节；
- 工具调用；
- 用户随口表达；
- 暂时性情绪；
- 领域专业内容。

因此不能简单设计成：

> 所有聊天全文都进入长期人格模型。

这样噪声会极大，而且非常容易误判。

更合理的长期原则是：

> **长期模型应该保存“提炼后的意义”，而不是无限保存原始聊天本身。**

---

# 14. Self-report Data：用户对自己的明确描述

Self-report 应该从普通 Semantic Data 中单独区分出来。

例如用户明确说：

> “我发现自己很难让事情悬着。”

> “我以前一直觉得要先完成目标，才能真正开始生活。”

> “最近我开始允许问题留到第二天。”

这类信息是：

> **用户对自身模式的主动表达。**

它对于人格发展模型是很强的证据。

但仍需要一个原则：

> **用户自我理解非常重要，但并不是永远不变的绝对事实。**

因为人会重新理解自己。

所以 Self-report 应被视为：

> 高价值、可更新的自我认识。

---

# 15. Longitudinal Pattern Data：长期发展模型真正的核心

长期 Companion 的重点不是记住所有事件，而是识别：

> **哪些模式在不同时间、不同情境中反复出现。**

例如：

> 用户在重要任务未闭环时，更容易推迟休息。

如果只出现一次：

> 只是一次事件。

如果跨：

- 工作；
- 学习；
- 科研；
- 工具配置；
- 个人计划；

都反复出现，才逐渐变成值得关注的长期 Pattern。

因此长期人格 / 心智发展模型真正应该依赖：

> **跨时间、跨情境、重复出现的模式。**

---

# 16. Longitudinal Pattern 不是简单统计

例如：

> “用户这个月深夜工作 8 次。”

这是一个统计事实。

但并不等于：

> “用户总在逃避生活。”

真正有意义的是：

- 深夜工作是否总与未完成的重要任务一起出现；
- 是否在任务形成闭环后明显停止；
- 用户是否表达过“没做完就无法放下”；
- 在没有 deadline 时是否也出现；
- 是否逐渐发生变化。

因此：

> Pattern 需要行为、情境、用户反馈共同解释。

---

# 17. Relationship Data：宠物如何学会与用户相处

Relationship Data 不主要用于判断：

> 用户是什么样的人。

而是用于判断：

> **宠物应该怎样与这个用户相处。**

例如：

- 用户是否喜欢被提醒；
- 是否讨厌频繁休息提示；
- 哪种表达方式比较自然；
- 用户是否接受直接 Challenge；
- 哪些提醒被用户拒绝过；
- 用户通常什么时候愿意深度 Reflection；
- 哪些宠物表达方式已经形成共同习惯；
- 宠物过去已经说过什么，避免重复。

这使宠物能够逐渐形成：

> 与具体用户独特的互动关系。

---

# 18. 长期模型不应该无限膨胀

一个用了三年的 Companion，不应该拥有：

> 数万条“用户人格特征”。

真正理想的情况反而是：

> 使用越久，对用户的理解越浓缩。

例如长期 Personal Model 可能只有：

- 少量稳定倾向；
- 少量长期发展张力；
- 若干用户确认过的 Self Insights；
- 当前 1–3 个主要 Growth Themes；
- 若干历史 Growth Chapters；
- 一些关系偏好。

也就是说：

> **长期理解应该越来越清晰，而不是越来越庞杂。**

---

# 19. 从大量数据到少量意义：数据漏斗

一个非常重要的整体思想是：

```text
大量原始信息
        ↓
可识别事件
        ↓
用户相关行为
        ↓
值得保留的经历
        ↓
跨情境 Pattern
        ↓
少量长期 Insight
        ↓
1–3 个当前发展主题
```

真正决定宠物如何理解用户的，不是底层海量数据，而是最上层少量、经过验证的发展主题。

可以把这一点概括为：

> **数据很多，长期结论应该很少。**

---

# 20. 信息应该拥有不同“生命周期”

不是所有信息都值得长期保存。

可以从概念上区分四个层级。

---

## 20.1 短期状态信息

例如：

- 当前时间；
- 当前 session 状态；
- 是否持续工作；
- 当前任务环境。

作用：

> 当前状态判断。

这种信息主要服务当下。

---

## 20.2 会话 / 阶段摘要

例如：

> 今天出现了几次长时间工作。

> 用户两次主动让未完成任务留到第二天。

作用：

> 短期趋势理解。

---

## 20.3 长期证据

例如：

> 用户在多个不同情境中，都表现出类似的停止困难。

作用：

> 支持 Pattern 与发展假设。

---

## 20.4 Stable Insight / Growth Narrative

例如：

> 过去用户主要通过目标与规划维持推进，现在正在学习让一部分事情保持未完成。

这才属于：

> 真正长期的 Personal Model。

---

# 21. Raw Data 应该“衰减”

整个系统不应该形成：

> 永久保存全部行为细节。

更符合 Companion 的方式是：

```text
原始状态
↓
逐渐淡出

阶段经历
↓
被压缩

有意义 Pattern
↓
保留更久

用户确认的 Insight
↓
长期存在

Growth Chapter
↓
成为共同历史
```

这和人的记忆也更加类似：

> 我们并不记得每一分钟发生了什么，但会记得重要经历和自己因此发生了怎样的变化。

---

# 22. 什么信息不应该默认收集

为了避免产品变成监控系统，建议明确：

以下信息不应成为默认采集对象：

- 全量键盘输入；
- 全量浏览历史；
- 所有窗口内容；
- 所有文件内容；
- 屏幕持续截图；
- 私聊软件内容；
- 鼠标轨迹；
- 摄像头数据；
- 麦克风持续监听；
- 精确位置轨迹；
- 与核心陪伴目标无关的全量系统行为。

原因不仅是隐私。

还有：

> **这些信息中绝大多数对人格发展模型是噪声。**

---

# 23. 本项目不是 Life Logging

这是需要明确的产品边界。

目标不是：

> 把用户整个人生数字化记录下来。

目标是：

> **只捕捉那些真正有助于理解用户如何生活、如何做选择、如何发生变化的信息。**

所以：

> 记录得多 ≠ 理解得深。

甚至很多时候：

> 收集过多数据反而会让理解更差。

---

# 24. 外部数据可以是增强项，而不是核心依赖

未来某些外部信息可能有帮助，例如：

- Calendar：帮助理解 deadline 与特殊工作节奏；
- GitHub / 项目系统：辅助理解长期项目是否推进；
- Task Manager：了解用户主动设定的目标；
- Journal / Notes：提供用户主动书写的反思；
- 健康 / 睡眠：如果用户明确愿意接入，可辅助理解作息。

但这些都不应该成为：

> 第一版 Companion 才能工作的必要条件。

现阶段更适合坚持：

> 核心模型必须能够从少量、高质量数据中工作。

---

# 25. “能看到”“能保留”“能用于人格推断”不是一回事

一个非常重要的概念边界是：

> 系统临时能够使用某个信息，不代表应该长期保存；长期保存，也不代表可以拿来做人格推断。

例如：

### 当前时间

可以用于：

> 判断是不是凌晨。

但没有必要成为长期人格证据。

---

### Hermes 自动 retry

可以用于：

> 理解任务是否困难。

但不能用于：

> 判断用户是否执着。

---

### 用户主动说“今天先到这里”

既是：

> 用户行为。

也可能在长期重复后成为：

> 成长证据。

---

### 原始会话全文

可能需要临时理解。

但长期更应该保留：

> 提炼出的自我陈述、Pattern 或 Growth Insight。

---

# 26. Companion 长期真正应该知道什么

从长期陪伴角度，真正重要的不是：

> 用户所有细节。

而是少量高价值信息，例如：

## 26.1 用户较稳定的倾向

例如：

- 倾向深入研究；
- 对证据要求较高；
- 有较强长期目标感。

---

## 26.2 用户长期反复出现的发展张力

例如：

```text
Future ↔ Present
Control ↔ Openness
Exploration ↔ Commitment
Persistence ↔ Letting go
Achievement ↔ Experience
```

---

## 26.3 用户自己认可的 Self Insights

例如：

> “未完成的事情很容易持续占据我的注意力。”

---

## 26.4 当前正在发生的成长

例如：

> 最近开始更容易在问题尚未解决时结束一天。

---

## 26.5 用户与宠物如何相处

例如：

> 不喜欢频繁提醒，但愿意在月底进行深入复盘。

---

# 27. 数据的意义必须清楚

未来任何一类数据进入系统前，都应该能回答：

> **为什么要知道它？**

它至少应该属于以下目的之一：

### State

帮助理解用户此刻状态。

### Evidence

帮助验证长期 Pattern。

### Context

帮助避免错误归因。

### Relationship

帮助宠物学会如何与用户相处。

如果一个信息不属于这些目的之一，就需要认真质疑：

> 是否真的有必要收集？

---

# 28. 数据收集不能反过来塑造用户行为

还有一个容易忽视的问题：

如果系统展示大量：

- 工作时长；
- 夜间次数；
- 高压次数；
- 各种分数；
- 行为排名；

用户可能开始：

> 为了指标而生活。

这与我们的产品愿景冲突。

因此底层即使存在大量数据分析，前台也应该尽量：

> **叙事化，而不是 KPI 化。**

例如：

底层可能知道：

> 某种模式出现频率下降。

前台更适合表达：

> “以前你很难把没有解决的问题留到第二天，最近这件事好像越来越普通了。”

而不是：

> “Uncertainty Tolerance +13%。”

---

# 29. Companion Data Model 与人格发展模型的关系

最终链路不是：

```text
数据
↓
人格标签
```

而应该是：

```text
信息
↓
事实观察
↓
长期重复
↓
Pattern
↓
Development Hypothesis
↓
用户校准
↓
Self Insight
↓
Growth Narrative
```

每往上一层：

- 信息数量减少；
- 意义增加；
- 解释风险增加；
- 所以需要更严格的证据与用户参与。

---

# 30. 当前可以确立的 Data Invariants

现阶段可以先明确以下原则。

### Invariant 1

**Collect minimally.**

只收集真正必要的信息。

---

### Invariant 2

**Raw data should decay.**

原始信息不应无限永久积累。

---

### Invariant 3

**User actions outweigh Agent telemetry.**

用户自己的选择比 Agent 自主行为更能说明用户。

---

### Invariant 4

**Context is required before interpretation.**

行为必须放在情境中理解。

---

### Invariant 5

**Long-term models should store abstractions, not surveillance logs.**

长期模型应该保存抽象后的理解，而不是监控日志。

---

### Invariant 6

**Self-reports are strong evidence, not absolute truth.**

用户自我陈述非常重要，但允许更新和变化。

---

### Invariant 7

**Sensitive semantic data should be distilled before becoming long-term memory.**

敏感会话信息进入长期模型前，应尽量被提炼。

---

### Invariant 8

**Every datum must have a clear purpose.**

每一种信息都必须明确服务于 State、Evidence、Context 或 Relationship。

---

### Invariant 9

**If data does not improve companionship or growth understanding, do not collect it.**

如果不能明显改善陪伴或成长理解，就不应默认收集。

---

### Invariant 10

**The long-term user model should become smaller and clearer over time.**

长期模型应该越来越清晰、浓缩，而不是越来越庞杂。

---

# 31. 目前最重要的边界

到目前为止，可以把 Companion Data Model 的边界概括为：

> **宠物不需要知道用户的一切。**

它真正需要知道的是：

> 用户此刻是否处于值得关心的状态；

> 用户在重要选择和不确定性面前通常如何回应；

> 哪些行为模式在不同时间、不同情境中反复出现；

> 用户自己如何理解这些经历；

> 这些模式最近有没有发生变化；

> 宠物应该以怎样的方式与这个用户相处。

---

# 32. 与项目整体愿景的关系

这个数据设计最终服务的不是：

> 更强大的用户画像。

而是：

> 更自然、更可信、更长期的陪伴。

理想状态是：

用户用了几年以后，宠物不是拥有一份巨大的监控档案。

而是拥有：

> 几段真正重要的共同经历；

> 对用户少量但越来越准确的理解；

> 对用户正在经历什么变化的长期记忆；

> 一套越来越适合彼此的相处方式。

这才符合：

# Co-evolving AI Companion

的核心理念。

---

# 33. 本阶段暂不讨论的内容

为了保持当前讨论聚焦，以下内容留到后续完成项目调研之后再决定：

- 数据库类型；
- Schema / 字段设计；
- Event 格式；
- 具体数据保留时长；
- 算法；
- Pattern 检测方法；
- Confidence 计算；
- LLM 调用方式；
- 本地模型还是云模型；
- 向量数据库；
- 隐私加密实现；
- 桌面端采集方式；
- Hermes Hook / Plugin / API 设计；
- ChatGPT 网页数据获取方式；
- 手机端同步技术；
- 具体技术栈。

这些属于：

> **实现方案**

而当前阶段主要做：

> **需求、边界、产品哲学与心智模型定义。**

---

# 34. 下一阶段继续讨论的方向

在不进入具体技术实现的前提下，下一步更适合继续讨论：

## A. Companion 的“通用心智发展维度”

例如：

- Future ↔ Present
- Control ↔ Openness
- Persistence ↔ Letting go
- Exploration ↔ Commitment
- Achievement ↔ Experience

需要进一步讨论：

> 哪些维度真正值得长期观察，哪些过于主观或重复。

---

## B. 用户成长到底如何被定义

需要继续明确：

- 什么叫“发展”；
- 什么叫“整合”；
- 什么不是成长；
- 如何避免 Companion 自己定义“更好的人”。

---

## C. 宠物自身如何被用户经历塑造

需要继续讨论：

- 性格如何变化；
- 哪些变化应该很慢；
- 哪些是宠物原生性格；
- 哪些是关系中共同形成的特征。

---

## D. Growth Narrative 应该如何形成

继续讨论：

> 怎样从大量经历中形成类似《悉达多》《鱼不存在》那样真正有意义的成长叙事，而不是普通总结。

---

# 35. 一句话总结

Companion Data Model 的目标不是：

> **知道用户越多越好。**

而是：

> **只知道那些真正值得知道的东西，并把它们慢慢变成理解，而不是监控。**

可以用一句英文概括：

> **Collect little. Understand deeply. Remember what matters.**

中文：

> **少收集，深理解，只记住真正重要的东西。**
