## 1. Executive Summary（执行摘要）

Coeva V1 的跨会话记忆体验不佳，其根本原因并非单纯“缺少向量搜索”，而是**系统级的数据本体混淆、准入控制缺失、新旧时序失真与表达控制失调**。在 V1 中，用户随手键入的问候、调试、瞬时吐槽与长期目标被无差别平铺存盘；检索层机械地通过 N-gram 模糊字面匹配并在命中时刚性塞入 System Prompt；大模型在 Prompt 权威暗示下频频产生强行翻旧账、话题劫持与新旧矛盾猜测。

Coeva V2 架构确立了**“平级成长伙伴（Companion）”而非“用户生产力画像器（User Profiler）”**的技术底座，核心创新与架构决策如下：

1. **确立四大顶层系统分权立界**：
   - **Context（语境面）**：“现在正在发生什么” —— 瞬时工作记忆与最近多轮滑动上下文；
   - **Memory（记忆面）**：“过去发生过什么 / 用户明确表达过什么” —— 不可篡改的经历事实底座；
   - **Understanding（理解面）**：“这些经历可能意味着什么” —— 需与用户双向校准的候选假说与共识；
   - **Narrative（叙事面）**：“经过时间沉淀后，我们如何共同回看一段时期” —— 宏观人生章节与演变印记。
2. **重构记忆准入与两阶段写入调和（Admission & Write-time Reconciliation）**：
   - 建立严格的记忆准入门控（Admission Gate），直接将无记忆价值的寒暄、纯技术调试与瞬时废话拦截为 `NOOP`，拒入长期存储；
   - 借鉴 Mem0 的两阶段写入决策思想：新事实入库前先召回相似历史，由轻量推理裁定 `ADD / UPDATE / INVENTORY / NOOP`，在写入源头消解冲突，坚决拒斥 ADD-only 垃圾累积。
3. **建立时序双时间戳置失效模型（Bitemporal Invalidation）**：
   - 引入现实成立时间（`valid_from`）与失效时间（`invalidated_at`），区分“历史事实”与“当前有效事实”；
   - 当用户偏好发生逆转（如“过去喜欢 A，现在改喜欢 B”）时，**置失效老事实并保留继承链接（`superseded_by`），绝不物理抹除历史轨迹**，完美兼顾当前有效认知与长期心智演进追溯。
4. **业界首创“三级门控分离”（Retrieved ≠ Injected ≠ Spoken）**：
   - **Recall Gate（回忆门）**：决定在当前用户输入下，检索出的记忆是否应被系统激活唤醒；
   - **Injection Gate（注入门）**：决定激活的记忆以何种结构、何种预算、何种非强制性提示注入推理上下文；
   - **Expression Gate（表达门）**：决定大模型在知道这段往事的前提下，是否值得在回复中对用户说出口。彻底践行 **“80/15/5” 节律与 “Silence Is Valid”** 哲学。
5. **本地轻量与全链路白盒证据链（Local-First & Full Provenance）**：
   - 坚持底层结构化存储与顶层人类可读 Markdown 结合；
   - 伴生体的任何高层心智理解必须沿着 `Confirmed Insight → Hypothesis → Observation → Episode / Memory → Raw Evidence` 完整回溯，支持用户直接查看“你为什么这样认为”，并赋予用户显式否认与修正权。

## 2. Why V1 Fails（V1 失效根本原因剖析）

根据前置事实审计（`cross-session-long-term-memory-fact-audit.md`），V1 的根本缺陷可解构为以下 5 大失控：

```text
               ┌────────────────────────────────────────────────────────┐
               │                  V1 链路失效全景图                      │
               └────────────────────────────────────────────────────────┘
用户输入: "hi", "测试", "这代码烦死了"        用户输入: "昨天聊了什么", " WA_TranslucentBackground "
               │                                                  │
               ▼ (准入盲目: 无过滤无结构)                         ▼ (分词机械: 专有词切碎, 意图丢失)
┌──────────────────────────────────────┐          ┌──────────────────────────────────────┐
│  Slices 表无差别永久堆叠             │          │  N-gram 字符滑窗 & LIKE '%kw%'       │
│  - 57.1% 为重复/浅层调试切片         │          │  - 语义相同换词 100% 漏召回          │
│  - 无 session / project 上下文       │          │  - 通用词引发 46.2% 语义漂移误召回   │
└──────────────────────────────────────┘          └──────────────────────────────────────┘
               │                                                  │
               └───────────────────────┬──────────────────────────┘
                                       ▼ (调和缺失: 新旧相反观点共存)
                       ┌──────────────────────────────────────────────┐
                       │  ORDER BY timestamp DESC 机械截断 Top-K      │
                       │  - 毫无相关度分数度量, 记忆权重绝对平等      │
                       │  - 矛盾事实同时注入, 迫使 LLM 猜度           │
                       └──────────────────────────────────────────────┘
                                       │
                                       ▼ (门控失调: Retrieved = Injected = Spoken)
                       ┌──────────────────────────────────────────────┐
                       │  刚性拼入 System Prompt:                     │
                       │  "这是真实聊过的事, 请自然作答证明你记得"     │
                       └──────────────────────────────────────────────┘
                                       │
                                       ▼
                       ┌──────────────────────────────────────────────┐
                       │  伴生体表现:                                 │
                       │  - 话题被误召回记忆劫持 (Topic Hijacking)     │
                       │  - 面对当下提问强行翻旧账 (Forced Callback)  │
                       │  - 避风港崩溃: 用户受挫时反而长篇大论说教     │
                       └──────────────────────────────────────────────┘
```

1. **Memory Admission 缺失**：没有设立记忆准入门禁，所有前端投喂无差别持久化；
2. **时序与演化失真**：没有区分“过去的事实”与“现在的偏好”，观点反转时无法自动废弃旧事实；
3. **上下文感知盲区**：切片缺少项目（Project）、工作区（Workspace）与会话（Session）绑定，多工程并行时必然串扰；
4. **门控三位一体粗暴绑定**：系统误以为“搜到了相关历史”就等于“必须注入上下文”，进而等于“必须在气泡里对用户说出来”；
5. **记忆与自模型割裂**：用户校准确认的共识（Insights）沉淀在孤岛表中，日常对话检索完全不读。

## 3. Design Goals & Non-Goals（设计目标与非目标）

### 3.1 核心设计目标 (Design Goals)
- **G1. 严格准入与分层清晰**：明确区分瞬时上下文、真实经历、客观事实、用户偏好与心智理解，非必要不入长期存储；
- **G2. 动态时序与冲突消解**：原生支持事实的时效性演进，偏好变化时自动使旧认知失效，并完整保留历史演化轨迹；
- **G3. 独立的三级门控（Retrieved ≠ Injected ≠ Spoken）**：建立 Recall、Injection、Expression 三级独立裁决，让伴生体学会优雅地保持沉默；
- **G4. 避风港绝对优先（Sanctuary Override）**：在用户情绪受挫或高压状态下，情绪安抚与低认知负荷陪伴强制覆盖一切往事回忆与反思；
- **G5. 全链路可解释与用户主权（Calibrated & Traceable）**：伴生体的高层心智理解可追溯至微观证据，用户可随时查阅、修正、标记失效或否认；
- **G6. 本地轻量与工程解耦**：架构逻辑完全与具体向量库、Embedding 模型解耦，不引入重型外部服务依赖，适配单机桌面常驻。

### 3.2 明确非目标 (Non-Goals · 严禁过度工程化)
- **NG1. 不构建通用企业级知识图谱**：不引入 Neo4j、FalkorDB 等重型图数据库，不追求海量实体多跳推理；
- **NG2. 不构建商业客服式静态用户画像（No Rigid Persona）**：不生成给第三方看的打标式用户 Profile，不把人类标签化；
- **NG3. 不追求“记忆越多越好”**：不以全量保留所有交互为荣，以准确、适时、克制为美；
- **NG4. 不搞云端托管 Memory SaaS**：所有数据与心智资产归属于用户本地文件系统与本地 SQLite；
- **NG5. 不采集外部 Agent 的私密正文**：严格恪守数据面隔离底线，不采集 CoT、不保存外部工具完整返回、不截获 Prompt 全文；
- **NG6. 不赋予伴生体无监管自编辑权**：严禁允许大模型在无人类确认的前提下随意篡改关于用户的高层认知结论。

## 4. Product Philosophy & Invariants（产品哲学与架构不可违背定理）

本系统的所有数据流、存储结构与逻辑流转，必须受制于以下 10 项架构定理（Architecture Invariants）：

| 架构定理 | 核心内涵与工程约束 |
| :--- | :--- |
| **INV-1. Evidence ≠ Interpretation**<br>（证据不等于解释） | 原始经历/切片是客观发生的不可变事实（Evidence）；从经历中提炼的倾向、结论与心理分析是主观解释（Interpretation）。二者在存储与表达上物理隔离，解释永远不得伪装成事实。 |
| **INV-2. Past Truth ≠ Current Truth**<br>（过去真实不等于当前有效） | “用户过去曾喜欢 X”与“用户现在偏好 Y”同为真实。系统必须显式表达有效时间范围，新偏好生效时废弃旧偏好，但绝不物理抹除历史演进痕迹。 |
| **INV-3. Retrieved ≠ Injected ≠ Spoken**<br>（召回不等于注入，注入不等于开口） | 检索命中（Retrieved）只代表系统后台想起了往事；注入上下文（Injected）需评估是否具有背景价值；开口表达（Spoken）需通过表达门控审批。严禁单向直通。 |
| **INV-4. Silence Is Valid**<br>（沉默是合法且受尊重的常态） | 检索返回空是常态；检索命中但系统决定不注入是常态；注入了但回复中一字不提更是常态。伴生体不需要不断提及旧事来证明自己的记忆能力。 |
| **INV-5. User Voice > Telemetry Inference**<br>（用户亲口表达高于行为遥测推断） | 用户亲口说出的偏好与认知，认识论权重绝对高于从数十次 Agent 工具日志中反向挖掘的统计模式。统计推断只能作为候选参考，永远不得覆盖用户明示。 |
| **INV-6. Candidate Understanding ≠ Confirmed Insight**<br>（候选假说绝非确定共识） | 伴生体对用户的任何性格、工作模式的理解，未经用户明确校准（Yes / Partly）前，始终属于“候选假说（Candidate）”，在 Prompt 中必须标明不确定性。 |
| **INV-7. No High-level Belief Without Provenance**<br>（无证据溯源则无高层信念） | 伴生体的任何高层判断必须能够枚举出其支撑的底层证据链。无法提供溯源指针的认知结论在校验阶段直接视为无效数据。 |
| **INV-8. Deletion Must Propagate Semantically**<br>（删除必须发生语义级联传播） | 当用户删除某条原始敏感记忆后，以此为核心支撑的派生假说与章节索引必须触发重算、降权或软标记，严禁原始数据删除后派生结论依然大摇大摆留存。 |
| **INV-9. Sanctuary Overrides Recall Expression**<br>（避风港熔断绝对覆盖记忆表达） | 当 Sanctuary Guard 检测到用户处于烦躁、疲惫、高负荷工作或极度挫败状态时，记忆表达门与反思系统强制关闭，严禁借题发挥与翻旧账。 |
| **INV-10. Memory Must Not Self-Reinforce Through LLM Echo**<br>（记忆绝不可通过大模型回音壁自我污染） | 伴生体在回复中复述的历史记忆必须携带 Feedback 围栏，下一轮交互将该消息存盘时自动剥离历史围栏内容，彻底阻断自产记忆自我强化的死循环。 |

## 5. Memory Ontology（记忆本体论：什么才叫 Memory）

在 Coeva V2 中，摒弃将所有输入平铺为“Slice”的旧做法，确立严格的概念分级本体：

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│                            Coeva 记忆本体层次划分                              │
├──────────────────────────────────────────────────────────────────────────────┤
│ 4. 叙事层 (Narrative)     │ 成长章节 (Growth Chapters)、人生里程碑 (Milestones)│
│    "我们如何回看一段时期"  │ - 宏观叙事文本，只读，周期性共创生成，不参与日常小检索│
├───────────────────────────┼──────────────────────────────────────────────────┤
│ 3. 理解层 (Understanding) │ 认知共识 (Confirmed Insights) / 候选假说 (Hypotheses)│
│    "经历可能意味着什么"    │ - 行为模式与心智理解，必须带置信度与证据溯源，需用户校准│
├───────────────────────────┼──────────────────────────────────────────────────┤
│ 2. 长期记忆层 (Long-Term) │ 原子事实 (Fact) / 长期偏好 (Preference) / 经历 (Episode)│
│    "过去发生了什么/用户明示"│ - 经准入与调和后沉淀的稳定事实，具备时间有效性标记与衰减│
├───────────────────────────┼──────────────────────────────────────────────────┤
│ 1. 瞬时语境层 (Context)   │ 短期工作记忆 (Working Memory) / 临时状态 (State/Mood) │
│    "现在正在发生什么"      │ - 会话内多轮消息缓存，空闲/退出时自动清空或进入巩固管道 │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 5.1 各类信息项属性定义与生命周期判定表

| 信息类型 (Ontology Unit) | 所属系统 | 是否属于 Memory | 典型示例 | 默认生命周期 | 是否允许自动生成 | 是否需用户确认 | 是否参与日常 Recall |
| :--- | :--- | :---: | :--- | :--- | :---: | :---: | :---: |
| **Greeting / Ping** | Context | **NO** | `hi`, `早安`, `测试气泡` | 即用即弃 (Turn End) | NO | NO | **NO** |
| **Temporary Mood** | Context | **NO** | `今天真累`, `好困啊` | 瞬时 (4~8 小时失效) | NO | NO | **NO** (仅驱动姿态) |
| **Temporary Task Note** | Context | **NO** | `等会看下这个按钮` | 任务级 (会话结束失效) | NO | NO | **NO** |
| **Episodic Interaction** | Memory | **YES** | 某次完整的报错排查与对话 | 永久存盘 (参与证据链) | YES | NO | **Conditional** (显式查往事) |
| **Factual Statement** | Memory | **YES** | `这个项目基于 PySide6` | 长期 (直到被更正) | YES (LLM抽取) | NO | **YES** |
| **User Preference** | Memory | **YES** | `复杂任务偏好先稳定架构` | 长期 (直到被 superseded) | YES (LLM抽取) | 可选 | **YES** (高优先级) |
| **Relationship Rule** | Memory | **YES** | `不要在深夜提醒我休息` | 长期 (强约束规则) | YES (LLM抽取) | **YES** (推荐) | **YES** (高优先级) |
| **Candidate Hypothesis**| Understanding | **NO** | `面对摩擦时倾向于收缩边界` | 待审状态 (动态演进) | YES (规则挖掘) | **需校准** | **NO** (仅校准页可见) |
| **Confirmed Insight** | Understanding | **NO** | `双方确认: 倾向于充分授权` | 长期心智 (有效版本) | NO (人类批准) | **YES (已确认)** | **YES** (作为背景) |
| **Growth Chapter** | Narrative | **NO** | 《从躬身入局到战略放手》 | 物理永久 (Markdown) | 双方共创 | **YES (共写留白)**| **NO** (仅宏观翻阅) |

## 6. Context vs Memory vs Understanding vs Narrative（四大顶层系统分立）

为杜绝 V1 中“随手一句吐槽直接变成假说”或“大模型生成的虚构总结反向污染真实切片”的恶疾，V2 确立四大系统单向单职责架构：

```text
  ┌──────────────┐
  │   Context    │  "现在发生什么" (前端输入、多轮会话队列、当前负荷、当前工程)
  └──────┬───────┘
         │ Admission Gate & Consolidation (准入与抽取)
         ▼
  ┌──────────────┐
  │    Memory    │  "过去发生了什么" (原子事实、稳定偏好、经历事件、溯源快照)
  └──────┬───────┘
         │ Pattern Mining & Attribution Gate (归因挖掘与证据归纳)
         ▼
  ┌──────────────┐
  │Understanding │  "这意味着什么" (候选假说、透镜评估、双方校准共识、相处默契)
  └──────┬───────┘
         │ Chapter Synthesis & Human Co-authoring (宏观沉淀与共创留白)
         ▼
  ┌──────────────┐
  │  Narrative   │  "共同走过的历程" (人生章节、成长史诗 Markdown、里程碑画卷)
  └──────────────┘
```

### 6.1 严格的读写权限单向矩阵

| 发起方系统 \ 目标系统 | Context (语境) | Memory (记忆) | Understanding (理解) | Narrative (叙事) |
| :--- | :---: | :---: | :---: | :---: |
| **Context** | 自由读写 | **只读** (受三级门控约束) | **只读** (仅读取已确认共识) | **禁读** (日常交互不读章节) |
| **Memory** | **禁写** | 自由增删改 (受时序调和) | **禁写** (事实层不得擅自推导) | **禁写** |
| **Understanding** | **禁写** | **只读** (作为归因分析证据) | 受校准流程修改 (人机共治) | **禁写** |
| **Narrative** | **禁写** | **只读** (作为历史素材) | **只读** (读取洞察作为支撑) | 受章节资格门写入与共创编辑 |

- **防污染硬规则 1**：Context 绝对禁止直接跨级生成 Understanding（严禁因用户说了一句“烦死了”，系统直接生成一条“用户抗挫力低”的假说）；
- **防污染硬规则 2**：Understanding 绝对禁止伪装成事实写回 Memory（伴生体的猜测即使置信度再高，也是理解，不是事实）；
- **防污染硬规则 3**：Narrative 绝对禁止反向修改底层 Memory（章节作为宏观文学叙事，其措辞与隐喻不得作为微观证据写回历史）。

## 7. Memory Lifecycle（记忆概念全生命周期）

一条信息从用户键盘键入到最终沉淀或淡忘，经历 10 个离散阶段：

```text
1. User Input (用户随手投喂/气泡回复)
       │
2. Short-term Working Context (加入单会话多轮工作上下文，维持当前交流)
       │
3. Admission Gate (准入判定: 瞬时寒暄/调试 -> 直接消费后丢弃 NOOP; 具实质内容 -> 放行)
       │
4. Candidate Memory Extraction (抽取候选原子事实与偏好: 提取 Fact, 时间, 实体, 情绪)
       │
5. Write-time Reconciliation (写入时调和: 预检相似历史，裁定 ADD / UPDATE / INVENTORY / NOOP)
       │
6. Long-term Store Persistence (入库落盘: 赋予 UUID、创建时间、valid_from、证据指针)
       │
7. Multi-Channel Retrieval (多通道召回: 词频 FTS5 + 向量语义 + 相对自然日区间 + Scope 过滤)
       │
8. Tri-Stage Gating (三级门控审批: Recall Gate -> Injection Gate -> Expression Gate)
       │
9. Offline Dreaming / Consolidation (离线做梦巩固: 空闲时慢速提炼 Observation 与更新统计)
       │
10. Aging, Invalidation & Selective Forgetting (演化淘汰: 衰减降权、置失效 superseded_by 或隐私硬删除)
```

## 8. Memory Admission（准入机制：什么有资格长期记住）

准入原则是解决数据堆积与噪音污染的第一道防火墙。V2 建立**明确的准入裁决分类标准**：

```text
                          ┌──────────────────────────┐
                          │   用户输入进入准入层     │
                          └─────────────┬────────────┘
                                        │
                    ┌───────────────────┴───────────────────┐
                    ▼                                       ▼
       [低熵/瞬时/环境信息]                       [高熵/事实/偏好/经历]
        - 浅层问候 (hi/早安)                       - 项目客观事实 (技术栈/架构)
        - 界面调试 (测试气泡/探头)                 - 长期工作偏好 (习惯/约束)
        - 瞬时状态 (好困/准备吃饭)                 - 关系相处要求 (不要提醒我休息)
        - 一次性备忘 (等会改按钮)                  - 深度个人反思 (心智复盘)
                    │                                       │
                    ▼                                       ▼
            【直接拒绝长期留存】                     【提取候选原子事实】
        Action = NOOP_LONG_TERM                     进入 Write-time Reconciliation
        (仅在当前 Context 消费)                     准备调和存盘
```

### 8.1 典型场景准入策略表

| 输入类别 | 典型用户文本样例 | Should Store? | 存储形态 | 预期有效期 (Validity) | 是否参与日常 Recall |
| :--- | :--- | :---: | :--- | :--- | :---: |
| **A. 问候寒暄** | `hi`, `你好`, `早安呀` | **NO** | 仅 Working Context 消费，不入库 | 0 (立即挥发) | **NO** |
| **B. 调试测试** | `测试气泡`, `测试发消息自动探头` | **NO** | 仅 Working Context 消费，不入库 | 0 (立即挥发) | **NO** |
| **C. 瞬时心境** | `今天真累`, `终于写完了好爽` | **Conditional** | 若表达极度受挫，作为 Episode 情绪快照存入；普通疲惫不入长期库 | 8 小时 (状态感知) | **NO** (不主动翻旧账) |
| **D. 一次性任务** | `等会记得测试下窗口缩放` | **NO** | 任务结束后由用户勾销，不入长期记忆 | 当前会话 | **NO** |
| **E. 项目客观事实**| `这个桌宠项目基于 PySide6` | **YES** | `Fact` (绑定 project_id) | 长期有效 (直到技术重构) | **YES** |

| **G. 偏好反转** | `现在我不想再每一步确认了` | **YES** | `Preference` (标记更新并使旧事实失效) | 长期有效 | **YES** (最新有效) |
| **H. 相处关系要求**| `不要在深夜弹气泡提醒我休息` | **YES** | `Relationship Rule` (高优先级交互约束) | 长期有效 | **YES** (硬性拦截) |
| **I. 长期愿景目标**| `希望做成真正共生的数字伙伴` | **YES** | `Goal / Intention` | 长期有效 | **YES** (适度共鸣) |
| **J. 自我深度反思**| `发现自己在架构没定时容易着急` | **YES** | `Reflection` (标记 user_asserted) | 长期有效 (作为成长证据) | **YES** (深度对话时) |

## 9. Working Memory / Conversation Context（工作记忆与会话上下文）

Coeva 与传统连续打字的 Chatbot 有根本不同：**伴生体是桌面低频驻留，用户两次投喂之间可能间隔数十分钟甚至半天**。

### 9.1 工作记忆架构规则
1. **多轮短期上下文缓存（Turn Buffer）**：
   - 维持单会话最近 3~5 轮的轻量交互上下文，确保短时间内追问（如“然后呢？”、“为什么这样？”）不发生语义断层；
2. **退出机制（Session Expiration & Idle Flush）**：
   - **空闲超时（Idle Timeout）**：连续无输入超过 30 分钟，Working Memory 自动标记封存；
   - **显式休眠（Pet Sleep）**：桌宠进入休眠状态时，自动触发会话结算；
3. **沉淀时机（Consolidation Timing）**：
   - **拒绝每轮同步抽取**：单次回复直接在内存进行，绝不因为后台写入而阻塞 UI 渲染；
   - **空闲结算与夜间做梦**：在 Session 封存后，或夜间系统空闲时，后台触发一次批量归纳抽取，静默进入长期记忆。

## 10. Episodic Memory（经历记忆：从 Session ID 到真实经历）

V1 将“同一个 `session_id`”粗暴定义为 Episode，导致单次长达数周未重启的客户端产生庞大臃肿的虚假会话。

### 10.1 Episode 语义重定义
> **定理**：**Episode 不是数据库连接会话，而是“在特定时空与项目背景下，人与伴生体共同经历的一件具有起承转合的闭环事件”。**

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│                              Episode 结构定义                                 │
├──────────────────────────────────────────────────────────────────────────────┤
│ - episode_id: UUID                                                           │
│ - project_id: 归属工程标识 (如 'co-evolving-companion')                      │
│ - time_window: (started_at, closed_at)                                       │
│ - topic_tag: 主题摘要 (如 '重构气泡渲染架构')                                │
│ - user_inputs: 期间用户投喂与回复列表 (包含原始情感标记)                    │
│ - telemetry_anchor: 关联的微观遥测摘要 (如 '发生3次报错, 最终测试通过')     │
│ - status: 'open' | 'closed' | 'archived'                                     │
│ - derived_facts: 从本 Episode 提炼出的原子事实与偏好外键列表                  │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **Episode 是容器还是记忆？**：Episode 是**结构化经历容器（Container）**。它保留不可篡改的事件快照与因果链；
- **防止大模型“编故事”**：Episode 的总结摘要（Summary）永远只作为**派生索引（Derived Artifact）**，绝不代替原始用户投喂作为第一事实源。任何争议发生时，以底层用户原始输入为准。

## 11. Semantic / Atomic Memory（原子事实与偏好建模）

从 Episode 中提炼的长期记忆，必须以精炼的**原子事实（Atomic Fact）**形式存在：

```text
原始用户表述:
"以后这个项目先把架构方案定清楚，写进 spec，再开始写代码实现。"
                    ↓
提炼出的原子事实 (Atomic Fact):
- fact_statement: "在复杂任务中偏好先确立架构规范并写入 Spec，再进行代码实施"
- category: "preference" (偏好)
- scope: "project" (归属于当前项目)
- provenance:
    source_episode_id: <UUID>
    raw_quote: "以后这个项目先把架构方案定清楚，写进 spec，再开始写代码实现。"
    actor: "user_asserted" (用户亲口明示，置信度 1.0)
- temporal:
    valid_from: "2026-10-18T10:00:00Z"
    invalidated_at: null
    superseded_by: null
```

### 11.1 关键防概括约束
1. **强引用原文（Raw Quote Integrity）**：每个原子事实必须携带 `raw_quote`。若用户追问“你为什么觉得我有这个偏好”，伴生体能直接展示用户当天的原话；
2. **来源权威度二分（Provenance Authority）**：
   - `user_asserted`：用户亲口所说，权威度为最高；
   - `system_inferred`：系统从连续多次行为中归纳推断，权威度为中，在 Prompt 中必须标明“推断猜测”。

## 12. Temporal Validity（时效性建模：过去真实 ≠ 当前有效）

这是消除“伴生体记忆新旧冲突”的核心理论底座。

### 12.1 状态时间线与时效字段
每个事实与偏好必须具备以下时态坐标：
- `occurred_at`：该事件或对话发生的物理时间；
- `valid_from`：该事实在现实中开始成立的时间；
- `invalidated_at`：该事实在现实中停止成立（被推翻、失效）的时间，未失效则为 `NULL`；
- `superseded_by`：若该事实被一个更新的偏好所取代，指向新事实的 `UUID`。

### 12.2 三大典型时态案例演练

#### 案例 1：偏好随时间推移发生反转
- **2026-01 用户投喂**：`"我喜欢深色主题。"`
  - 存储：`Fact_1: "偏好深色主题", valid_from: 2026-01, invalidated_at: NULL`
- **2026-10 用户投喂**：`"最近我更喜欢浅色主题。"`
  - 调和触发：检索到 `Fact_1` 与新输入对立；
  - 状态演进：
    - `Fact_1` 标记：`invalidated_at: 2026-10, superseded_by: Fact_2`
    - `Fact_2` 写入：`"偏好浅色主题", valid_from: 2026-10, invalidated_at: NULL`
- **当前回忆表现**：
  - 系统当前有效偏好检索，只召回 `Fact_2`（浅色主题）；
  - 若用户询问：“你记得我以前喜欢什么主题吗？”，系统溯源 `Fact_2 -> superseded -> Fact_1`，精准回答：“你以前很喜欢深色，10 月份换成了浅色”。**历史演化毫发无损，当下认知丝毫不乱**。

#### 案例 2：瞬时情绪的时态隔离
- **昨天**：`"今天很累。"`
  - 存储：标记为 Context 瞬时状态，`valid_from: 昨天, invalidated_at: 昨晚`；
- **今天**：用户正常工作；
  - **当前表现**：昨天的“很累”已自然过期失效，日常对话不予召回；只有当用户显式问及“昨天我状态怎么样”时，才在历史归档中作为已结束事实被翻阅。

#### 案例 3：项目技术选型重构
- **历史记录**：`"这个项目准备使用 React。"`
- **最新记录**：`"最终换成了 PySide6。"`
- **系统状态**：旧事实被标记失效并指向新事实。当提问“用什么框架写界面”时，只向 Prompt 注入 PySide6；当提问“我们最初考虑过什么技术”时，完整还原从 React 到 PySide6 的架构演化。

## 13. Contradiction & Supersession（冲突裁决策略对比与选型）

面对观点相反的记忆，业界存在三种策略：

```text
策略 A: Physical Overwrite (物理覆盖，直接用新内容替换旧行)
  - 弊端: 彻底抹除了用户的思想演变历程，无法回答“我过去怎么想的”。
  
策略 B: Keep Both + Latest Wins (新老共存，仅按时间逆序排)
  - 弊端: V1 的失败根因。多关键词搜索会导致新旧切片同时涌入 Top-K 注入，让大模型自相矛盾。

策略 C: Invalidate Old + Link Successor (置失效并链接后继，Graphiti 模式)
  - 优势: 100% 保持历史完整性；检索“当前”时过滤掉已失效项；检索“演化”时顺藤摸瓜。
```

> **Coeva 裁定**：
> **全面采纳策略 C（Invalidate Old + Link Successor）**。
> 坚决禁止物理删除用户的思想足迹，通过置失效标志位（`invalidated_at`）物理隔离当前推理上下文，彻底杜绝自相矛盾。

## 14. Salience（重要性度量：什么才叫“重要”）

V2 坚决拒绝让大模型主观打出虚浮的“1~5 分”。在 Coeva 体系中，记忆的**物理重要性由严谨的客观信号多维构成**：

```text
Salience (综合重要性) = f(Type_Weight, Evidence_Count, User_Assertion, Recency_Decay)
```

1. **类型固有权重 (Type_Weight)**：
   - `Relationship Rule`（相处红线与边界）= 1.0（最高）
   - `User Preference`（长期工作/生活习惯）= 0.8
   - `Project Fact`（工程关键技术决策）= 0.7
   - `Deep Reflection`（心智深度反思）= 0.7
   - `Casual Chat`（普通闲聊杂事）= 0.2
2. **证据支撑度 (Evidence_Count)**：
   - 借鉴 Hindsight 的 `proof_count`：同一观点在不同会话中被用户反复提及，重要度随对数曲线提升；
3. **用户确证加权 (User_Assertion)**：
   - 用户亲口强调（“记住这个”）或在自模型校准中确认（`Confirmed Insight`）= 乘数 1.5×；
4. **检索强度衰减 (Recency_Decay)**：
   - 借鉴 Mem0 的 Decay 机制：长期未被触碰激活的事实，在排序时权重平滑退火降至最低 0.3×，但不物理丢失。

## 15. Forgetting & Retention（遗忘、归档与隐私硬删除）

必须明确确立**“自然淡忘”与“隐私删除”不是同一个概念**：

```text
┌───────────────────────────┬────────────────────────────────────────────────────────┐
│ 遗忘类型                  │ 物理机制与语义表现                                    │
├───────────────────────────┼────────────────────────────────────────────────────────┤
│ 1. 检索强度衰减 (Decay)    │ 保持数据完整，因长期未用降低检索打分，让记忆自然沉睡   │
├───────────────────────────┼────────────────────────────────────────────────────────┤
│ 2. 时态失效 (Invalidation) │ 偏好改变时标记 invalidated_at，不再进入日常当前检索    │
├───────────────────────────┼────────────────────────────────────────────────────────┤
│ 3. 冷库归档 (Archival)     │ 移出日用检索索引，仅在用户翻看年鉴或显式回忆往事时可查 │
├───────────────────────────┼────────────────────────────────────────────────────────┤
│ 4. 用户标记"不再提及"      │ 用户明确指示"别再提这件事"，加入屏蔽名单，门控永久拦截 │
├───────────────────────────┼────────────────────────────────────────────────────────┤
│ 5. 隐私硬删除 (Hard Delete)│ 物理从数据库彻底抹除（GDPR 级），并启动派生数据清理    │
└───────────────────────────┴────────────────────────────────────────────────────────┘
```

## 16. Retrieval Pipeline（多通道检索逻辑管线）

检索管线的设计目标是**兼顾语义模糊匹配与专有名词精确度**，管线划分为 7 个纯逻辑阶段（技术实现无关）：

```text
1. Query Intent & Time Parsing
   ├── 提取自然语言相对时间 (昨天、上周、三个月前) -> 解析为绝对时间区间 [T_start, T_end]
   └── 识别是否属于显式寻源提问 (如"你还记得为什么...") -> 切换为溯源检索模式
         ↓
2. Context Scoping (工程与会话范围限定)
   └── 默认圈定当前 project_id 与 global scope，严格隔离无关工程
         ↓
3. Candidate Generation (多通道候选生成)
   ├── 通道 A: Lexical Channel (基于精确词与术语分词匹配)
   ├── 通道 B: Semantic Channel (基于整句语义相似度向量匹配)
   └── 通道 C: Temporal Channel (按时间区间范围命中)
         ↓
4. Score Fusion (无监督分值融合)
   └── 采用无参数、免调优的 Reciprocal Rank Fusion (RRF, k=60) 计算综合排序
         ↓
5. Temporal Validity Filtering (时态过滤)
   └── 默认丢弃 invalidated_at < NOW 的已失效事实 (显式问及往事除外)
         ↓
6. Salience & Decay Adjustment (重要度与衰减再平衡)
   └── 叠加类型权重、证据支撑度与访问衰减系数
         ↓
7. Top-K Candidates Output -> 提交至三级门控系统
```

## 17. Recall Gate（第一道门：回忆门控）

> **核心职责**：
> **回答：“系统已经检索到了相关历史，但在当下的情境中，是否允许唤醒这些记忆进入思考？”**

```text
                  ┌───────────────────────────┐
                  │ 检索候选结果到达 Recall Gate│
                  └─────────────┬─────────────┘
                                │
       ┌────────────────────────┴────────────────────────┐
       ▼                                                 ▼
[Sanctuary Guard 激活?]                           [用户提问意图检测]
- 用户心烦/受挫/连续高负荷                         - 是否显式询问往事?
- 情绪 flag == 'frustrated'                       - 属于普通功能性问路?
       │                                                 │
       ├───────────────────── 是 ───────────────────────┤
       ▼                                                 ▼
【强制静默 (Recall Suppressed)】                 【分流裁决】
拒绝唤醒任何历史记忆，保持极简陪伴               - 显式查往事 -> 放行 (High Priority)
输出: NO_RELEVANT_MEMORY                        - 强相关背景 -> 放行 (Background)
                                                - 弱相关/口头禅 -> 拦截 (Suppressed)
```

### 17.1 典型情境裁决矩阵
- **案例 A（问路场景）**：
  - 用户：“这个按钮颜色怎么改？”
  - 检索结果：“上个月调整桌宠皮肤时讨论过颜色配置”
  - **Recall Gate 裁决**：**拦截（Suppressed）**。用户在解决具体的即时技术编码问题，上个月的皮肤闲聊与当前工程任务无关，强行唤醒只会造成干扰。
- **案例 B（心智觉察）**：
  - 用户：“我感觉最近又有点急了。”
  - 检索结果：“两个月前曾有类似焦躁反思记录，后来通过拆分任务平复”
  - **Recall Gate 裁决**：**放行（Allowed as Empathetic Background）**。属于用户主动的情绪/心智交流，历史经历可作为共情支撑。

## 18. Injection Gate（第二道门：注入门控）

> **核心职责**：
> **回答：“经过 Recall Gate 允许唤醒的记忆，应当以何种结构、何种预算注入 System Prompt？”**

### 18.1 注入规范与硬预算约束
1. **字符预算物理红线（Context Budget）**：
   - 借鉴 Letta 的 Core Memory 设计，常设记忆区严格限制在 **300 汉字以内**；
   - 超过预算时，按 `Salience × Recency` 优先截断，杜绝无节制膨胀；
2. **非强制性背景提示协议（Non-Forcing Protocol）**：
   - 注入的记忆绝不得被描述为“必须向用户展示的事实”；
   - **标准 Prompt 包装格式**：

```markdown
<companion_background_memory>
【你与用户的过往经历参考（基准日期：{current_date}）】：
以下信息仅供理解语境参考。若与当前交互无直接关联，请绝对保持沉默，严禁生硬提及或强行翻旧账。
- [{valid_from}] 用户偏好: 复杂任务先定架构再实现 (证据: 亲口明示)
- [{valid_from}] 事实: 本项目前端运行在 PySide6 环境
</companion_background_memory>
```

3. **两类注入模式物理隔离**：
   - **Background Injection（背景型）**：用于日常交流，附带“不相关请忽略”指令；
   - **Direct Evidence Injection（查证型）**：用户主动问及往事时使用，附带完整原始引用 `raw_quote`。

## 19. Expression Gate（第三道门：表达门控）

> **核心职责**：
> **回答：“大模型在上下文里已经获知了这段往事，但伴生体这次是否应当张嘴对用户说出来？”**

这是 Coeva 区别于一切功利型 Agent 的灵魂之门。**知道，但选择不说，是最高级的情商与陪伴。**

```text
                           ┌──────────────────────────┐
                           │ 大模型生成回复文本草稿   │
                           └─────────────┬────────────┘
                                         │
        ┌────────────────────────────────┴───────────────────────────────┐
        ▼                                                               ▼
[用户主动询问往事?]                                            [日常普通交互]
例如: "你还记得我之前为什么..."                                例如: "今天继续改动画", "终于修好了"
        │                                                               │
        ▼                                                               ▼
【允许自然引用表达】                                           【执行表达约束审查】
直接告知记忆事实，无需避忌                                     - 是否在刻意证明"我记得你"? -> 删改
                                                               - 是否产生好为人师的说教感? -> 删改
                                                               - 记忆是否已作为默认背景生效? -> 保持沉默
```

### 19.1 经典情景表达判定

#### Case A（普通日常开工）
- 用户：“今天继续改 Vasu 动画。”
- 系统知道：“用户昨天也改了一整天动画，最后遇到了性能瓶颈。”
- **Expression Gate 裁决**：**绝对不要说**“你昨天也改了一整天”。
- **理由**：刻意复述昨日动态显得机械且充满监控感。伴生体只需轻声回应“好呀，慢慢理顺它”即可。记忆在幕后作为心智背景支撑，体现在语调的松弛感中，而非体现在言辞的显摆上。

#### Case B（完工告捷）
- 用户：“终于把这个崩溃 Bug 彻底修好了！”
- 系统知道：“三天前用户因为这个 Bug 情绪烦躁全搞砸了。”
- **Expression Gate 裁决**：**绝对不要提**“你三天前很烦躁”。
- **理由**：严禁在他人高兴时翻出黑历史。应直接为当下成果开心跳跃：“太棒啦！辛苦终于有着落了！”

#### Case C（用户主动寻源）
- 用户：“你还记得我当初为什么决定做 Native Idle 吗？”
- **Expression Gate 裁决**：**允许精准详实表达**。调用 Direct Evidence，引用当初的原因作答。

## 20. Memory → Self Model Bridge（记忆与自模型桥梁）

彻底理顺数据流向，杜绝自封真理与回音壁循环：

```text
  ┌─────────────────────────────────────────────────────────────┐
  │ 1. Memory Layer (记忆层: 客观事实与经历事实)                 │
  │    - 存储: Episodes, Atomic Facts, Raw Slices              │
  └──────────────┬──────────────────────────────────────────────┘
                 │ 持续累积 & Pattern 挖掘 (证据支撑)
                 ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ 2. Observation Layer (观察信念层: 借鉴 Hindsight)            │
  │    - 具备 proof_count (例: 8次印证) 与 source_memory_ids   │
  └──────────────┬──────────────────────────────────────────────┘
                 │ 心理灵活性六大透镜综合推理
                 ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ 3. Hypothesis Layer (候选假说层: 伴生体的主观心智理解)      │
  │    - 状态: 'candidate' (严禁写入 Memory, 仅在校准面板呈现)   │
  └──────────────┬──────────────────────────────────────────────┘
                 │ Human Calibration (人类校准: Yes / Partly / No)
                 ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ 4. Confirmed Understanding (已确认共识: 真正的自模型)       │
  │    - 状态: 'confirmed'，正式作为高层认知影响相处方式        │
  └─────────────────────────────────────────────────────────────┘
```

### 20.1 反馈环路守卫（Feedback-Loop Guard）
为彻底贯彻 **INV-10**，系统在 Prompt 组装与切片入库时执行特征标记：
- 被注入 Prompt 的理解与记忆被包裹在 `<companion_background_memory>` 围栏内；
- 当桌宠与用户交流完毕、系统将当前对话存为新切片时，**预处理器强制利用正则表达式剥离一切围栏文本**；
- 严禁将伴生体复述的历史话语重新提取为“新事实”，彻底终结认知自我闭环感染。

## 23. User Control & Sovereignty（用户主权：查看、修正与否认）

在 Coeva 体系中，用户对自己的记忆与伴生体的认知拥有最高裁决权：

1. **白盒可查（Visibility）**：
   - 用户可随时在图形面板中列出所有记忆，每条记忆均显示 `valid_from`、`occurred_at` 与关联的原始原话；
2. **更正与更替（Correction & Supersession）**：
   - 用户可对某条过时偏好直接点击“已改变”，系统引导输入新偏好，自动完成置失效链接；
3. **标记“不要再提”（Mute / Do Not Mention）**：
   - 某段经历用户不愿被伴生体唤醒，可一键标记“保持封存”，Expression Gate 永久禁言；
4. **彻底否认假说（Denial of Hypothesis）**：
   - 伴生体提出的候选假说，用户点击 `No` 否定，该假说立即永久作废，并记录为负向约束，伴生体永不再犯。

## 24. Deletion Propagation（删除传播机制：微观删除如何级联派生）

当用户执行 **Hard Delete（物理删除）** 某条原始切片时，系统遵循以下确定性级联传播规则：

```text
用户物理删除原始切片 S_0
         │
         ├── 1. 物理抹除底层记录: slices 表删除该行, JSONL 标记 tombstone
         │
         ├── 2. 检索索引同步驱逐: FTS5 索引与语义向量索引立即物理清除
         │
         ├── 3. 级联检查 Observation 信念层:
         │      ├── 找到所有引用 S_0 的 Observation
         │      ├── 移除 source_memory_ids 中的 S_0, proof_count 递减 1
         │      └── 若 proof_count == 0 -> 该 Observation 自动随之销毁
         │
         ├── 4. 级联检查 Hypothesis 假说层:
         │      ├── 若某假说失去了唯一支撑观察 -> 假说降级撤销 ('retracted')
         │      └── 若假说已有用户确认 ('confirmed') -> 保持共识有效, 但切断溯源外键
         │
         └── 5. 检查已生成的人生章节 (Chapter):
                └── 章节已是静态只读文件，不破坏 Markdown 文本排版，
                    但在元数据层面剔除该切片引用，并在档案审查中断开跳转链接。
```

## 25. Privacy Boundary（外部 Agent 隐私边界与授权分类）

严格执行数据面与控制面物理隔离：

| 数据要素 | 处理规则 | 存储位置 | 长期留存策略 |
| :--- | :--- | :--- | :--- |
| **用户在 Feeder / Bubble 的亲口输入** | 完整明文保留 (敏感模式可本地脱敏) | `slices` (SQLite) | 长期保存，受时态调和管辖 |
| **外部 Agent 工具调用名称 (tool_name)** | 保留枚举与签名 (如 `git_commit`) | `events` (SQLite) | 30 天 TTL 自动滚动清理 |

| **用户剪贴板 / API Key / 凭据** | **正则扫描脱敏拦截 (REDACTED)** | 不入库 | 0 (内存不留) |

## 26. Candidate Architectures（三大约束架构候选对比）

### 候选 A：Minimal Layered Memory（极简分层式架构 · 推荐演进路线）
- **架构描述**：在现有 SQLite 基础上，将存储拆分为 `facts` 与 `episodes` 两张轻量表，引入两阶段写入调和（ADD/UPDATE/DELETE/NOOP）与双时间戳（valid_from/invalidated_at），检索层接入 FTS5 + 本地极简语义嵌入 + RRF 融合，上层接入 Recall/Injection/Expression 三级门控。
- **复杂度**：中等；完全保持 Python 3.11+ 标准库与 SQLite 单文件，零外部服务。
- **本地适配性**：极高（冷启动 < 100ms，内存增加 < 30MB）。

### 候选 B：Episode-Centric Event Sourcing（会话事件溯源式架构）
- **架构描述**：以严格的 Episode 状态机为核心，所有切片与遥测均作为不可变 Event 追加至日志链，高层事实全部由物化视图（Materialized View）动态投影计算得出。
- **复杂度**：高；需要复杂的重放（Replay）与投影引擎，代码实现繁琐。
- **本地适配性**：中（在桌面端容易造成状态同步复杂与并发写冲突）。

### 候选 C：Client-Side Sidecar Memory Architecture（类 TDAI/Hindsight Sidecar 架构）
- **架构描述**：在本地启动独立的 Node.js 或 Docker 守护进程作为 Memory Gateway，桌面桌宠仅作为 HTTP Client 调用。
- **复杂度**：极高；运维复杂，极易出现端口冲突、进程保活失败与安装门槛。
- **本地适配性**：差（严重违反 Coeva 的免配置、轻量常驻桌宠原则）。

## 27. Recommended Architecture Direction（推荐架构方向）

> **结论**：
> **全面选定“候选 A：极简分层式架构（Minimal Layered Memory）”作为 Coeva V2 的核心架构演进路线。**
> 
> **架构定性**：
> 1. **核心底座**：纯本地单机 SQLite + 顶层 Markdown 人类可读档案；
> 2. **控制核心**：记忆准入裁决 + 两阶段写入调和 + 三级门控审批（Recall / Injection / Expression）；
> 3. **时空哲学**：双时间戳置失效模型 + 全链路证据追溯指针。

## 28. Scenario Walkthroughs（真实全场景推演验证）

### 场景 1：瞬时情绪自然消化
- **Day 1 晚**：用户投喂 `"今天真累。"`
  - **写入**：准入层识别为瞬时心境，标记 `valid_from: Day1_晚, invalidated_at: Day2_晨`，不作为长期原子事实入库；
  - **姿态**：伴生体当晚切换为 `REST` 动作，轻声回应“辛苦啦，歇歇眼睛”；
- **Day 4**：用户投喂 `"今天状态不错。"`
  - **Recall Gate**：Day 1 的疲惫早已失效，检索不召回；
  - **表现**：伴生体愉快跳跃（`JUMP`），绝不冒失说出“你三天前还说很累”。

### 场景 2：偏好演进与无痕更替
- **Month 1**：`"我喜欢每一步都确认。"`
  - 入库：`Fact_A ("偏好每步确认"), valid_from: Month1`
- **Month 3**：`"现在我更喜欢让 Agent 自己跑完。"`
  - 调和层：预检索命中 `Fact_A`，LLM 裁定为反转更新；
  - 执行：`Fact_A` 标记 `invalidated_at: Month3, superseded_by: Fact_B`；`Fact_B` 入库；
  - **当前交互**：日常编码时，系统只激活 `Fact_B`，行为策略自动放宽干预频率；历史演变完整保留在档案库。

### 场景 3：跨项目同名词隔离
- **Project A (桌宠)**：讨论 `"Vasu 的动画状态机"`
- **Project B (Web系统)**：讨论 `"Web 前端状态机"`
- **用户在 Project B 提问**：`"状态机这里有点问题。"`
  - **Context Scoping**：检索自动绑定 `project_id = 'Project_B'`；
  - **表现**：绝对不会把 Vasu 桌宠的动画逻辑翻出来，实现彻底的工程隔离。

### 场景 4：显式往事询问
- **用户提问**：`"你还记得我为什么决定先做 Native Idle 吗？"`
- **管线反应**：
  - Query Intent 识别为**显式寻源意图**；
  - Recall Gate 允许穿透历史归档与失效过滤；
  - Injection Gate 调取带 `raw_quote` 的历史原子事实；
  - Expression Gate 允许直述往事：“记得呀，当初你说先做 Native Idle 能保证零帧延迟”。

### 场景 5：问路不翻旧账（No-Memory Decision）
- **用户提问**：`"这个按钮颜色怎么改？"`
- **管线反应**：
  - 检索虽命中了上月桌宠调色记录；
  - 但 Recall Gate 判定当前属于具体代码问询，与旧事无关，输出 `NO_MEMORY_USE`；
  - 伴生体给出专业干练回答，绝不自作多情提起“上个月你也调过颜色”。

### 场景 6：避风港绝对熔断（Sanctuary Override）
- **用户情绪失控**：`"烦死了，又全搞砸了。"`
- **管线反应**：
  - Sanctuary Guard 瞬时红线熔断；
  - Recall Gate 与 Expression Gate 强制闭锁；
  - 伴生体安静趴下（`SLEEP/REST`），回复极其质朴接纳：“我在呢，先喘口气，代码跑不了。”；
  - 彻底杜绝“你上次搞砸后来重构好了”之类的有毒安慰。

### 场景 7：用户否认自模型假说
- **伴生体在面板呈现**：`"我感觉你最近更喜欢放手让 Agent 尝试"`
- **用户点击**：`"不太对 (No)"`
- **系统反应**：
  - 假说标记为 `retracted`；
  - 系统生成一条负向约束：“严禁假定用户喜欢放手”；
  - 伴生体后续行为立即回退至稳健提示策略，绝不再犯。

### 场景 8：敏感事实删除传播
- **用户操作**：删除 `"我准备申请某某大厂"` 这条切片
- **系统反应**：
  - 底层切片与向量索引物理抹除；
  - 扫描发现某 Observation 引用了此切片，移除外键指针，支撑计数递减；
  - 若这是该求职信念的唯一证据，该信念立即在认知层彻底蒸发；
  - 后续交互与宏观章节中永不再出现该大厂字眼。

## 29. Migration Principles（平滑迁移原则）

1. **零数据丢失底线**：
   - 现存 `data/companion_chronicle.db` 中的 42 条 `slices` 与 11.5 万条 `events` 必须 100% 物理保留；
2. **惰性分类迁移（Lazy On-Demand Migration）**：
   - 旧切片暂归入 `Legacy Raw Archive` 类别；
   - 系统不急于在升级瞬间一次性调用昂贵大模型重跑 42 条切片，而是在后续伴生体闲置“做梦”时逐步梳理；
3. **向后兼容双轨运行**：
   - 在新数据模型上线初期，保留只读旧接口，确保现有 UI 窗口无缝过渡。

| 潜在架构风险 | 风险成因 | 工程防范与缓解对策 |

| **R1. 写入调和增加延迟** | 每次随手投喂都调用 LLM 比对历史会导致交互迟滞 | **异步解耦**：投喂瞬间即刻存盘返回 UI 反馈，调和决策在后台异步线程完成，不卡主交互。 |
| **R2. 冲突判断漏判** | 小型 LLM 无法准确识别隐晦的偏好反转 | **宽松置失效**：若判断置信度低，标记 `ambiguous` 保留两者，等待用户在自模型面板显式校准。 |
| **R3. 本地嵌入资源超标** | 桌面端运行大型嵌入模型导致 CPU 占用过高 | **算法分层**：优先使用 FTS5 过滤至小候选集，仅在必要时调用微秒级本地精简模型计算余弦相似度。 |

## 32. Acceptance Criteria（架构验收达标断言）

本规范设计方案已严格达成以下验收准则（Acceptance Criteria）：

- [x] **AC-A. 不再把所有输入视为永久长期记忆**：通过准入层（Admission Gate）将寒暄、调试、瞬时备忘物理阻断为 `NOOP`；
- [x] **AC-B. 不再把“搜索到了”等同于“塞进 Prompt”**：通过 Recall Gate 与 Injection Gate 严格进行场景意图与字符预算过滤；
- [x] **AC-C. 不再把“塞进 Prompt”等同于“对用户说出来”**：通过 Expression Gate 坚决捍卫 Silence Is Valid 与 80/15/5 哲学；
- [x] **AC-D. 能准确表达“过去是真的，但现在已经变了”**：确立双时间戳（`valid_from` 与 `invalidated_at`）模型；
- [x] **AC-E. 能保留历史变化而非粗暴覆盖**：偏好演变采用置失效后继链接（`superseded_by`），全景保留思想演化；
- [x] **AC-F. 能表示不知道、不确定与矛盾**：候选假说显式携带置信度与 `ambiguous` 状态；
- [x] **AC-G. 记忆与自模型清晰分离但可追溯连接**：确立 Context → Memory → Understanding → Narrative 四层单向治理架构；
- [x] **AC-H. 所有高层理解都能追溯到真实证据**：强制要求带有 `raw_quote` 与 `source_memory_ids` 强外键；
- [x] **AC-I. 删除原始证据后派生理解存在明确规则**：确立了微观切片删除在 Observation、Hypothesis 与 Chapter 的级联清理传播路径；
- [x] **AC-J. 避风港绝对覆盖记忆表达**：Sanctuary Guard 激活时强制闭锁一切翻旧账与反思；
- [x] **AC-K. 保持本地极轻单机特性**：坚决拒斥 Docker、PostgreSQL、Neo4j，架构完全基于本地单机环境成立；
- [x] **AC-L. 彻底拒斥静态用户画像**：严禁自动生成不可变 Persona，伴生体永远定位为谦抑、平级的数字伙伴。
